# The Rust side owns the Session file

The Session is one file, `session.json`, in the app's own config directory: the Folder, the open Tabs with each Document's mode, the active Tab, the sidebar state, each Folder's Pinned list and the window frame. One file rather than one store per concern, for three reasons. A restore then reads one moment's state, so the Tabs, the sidebar and the window it brings back belong together. A Folder never holds Plumo's configuration (the glossary's definition of a Folder), so the Tab list and the Pinned lists need a home outside it, and the config directory is that home for everything else already. And when something goes wrong there is one file to read, and one file to delete to start over. It is written atomically, about 500 ms after any change, and flushed once more on quit.

The pieces have two owners by nature. The renderer alone knows the Tabs, the Folder and the sidebar; only the native side sees the window frame. Two owners of one file race each other, and a renderer-side debounce loses whatever changed in the last half second before ⌘Q, because the webview is torn down without a chance to flush.

## Decision

The Rust `session` module owns the file. The renderer hands over its part of the Session (`update_session`) on every change and reads the file back once at launch (`read_session`); it never debounces and never touches `window`. Rust keeps the last renderer state in memory (seeded from the file at launch, so a window move before the renderer reports cannot erase the open Tabs), merges the main window's frame in from its own Moved and Resized events, and does the one debounce, the atomic temp-file-and-rename write, and the flushes: on the window's close request, on `ExitRequested` and on `Exit` (the native Quit item terminates through `applicationWillTerminate`, which reaches the event loop as `Exit`).

The schema is validated in the renderer (`src/session/session-schema.ts`): an unknown `version` restores nothing and is rewritten by the renderer's first update. The Rust side treats the renderer's part as opaque JSON.

Rejected:

- **The renderer owns the file** and asks Rust for the frame: the renderer cannot flush at quit, so the last half second of changes is lost, and the frame would cross the boundary twice for nothing.
- **Each side keeps its own store** (the frame in a native window-state file, the rest in the webview's localStorage): two writers if they ever share a file, and localStorage is tied to the webview's data store, invisible to the user and not one file to inspect or delete.

Two consequences of "⌘W with zero Tabs closes the window; Dock reopen restores the Session" are settled here as well:

- On macOS the app stays running after its last window closes (`prevent_exit` on the user-initiated `ExitRequested`), and `Reopen` with no visible window rebuilds the main window from the config and reapplies the saved frame; the renderer boots and restores the Session as at launch.
- Close Tab stays enabled with no Document open (it leaves the manifest's `noteDependent` group), because a disabled native accelerator would swallow ⌘W before the renderer could close the window. The Window menu drops the predefined Close Window item so ⌘W has one owner.

## Consequences

- The renderer's saved-Tab state is at most one IPC call behind the file; there is no window in which a quit loses the last change.
- The saved frame is applied in `setup`, before the first paint; a frame that lands off every screen is ignored. The dev build's centring only happens when no frame was restored.
- In the browser the Folder fixture answers both commands and keeps the Session in localStorage, so a page reload stands in for a relaunch in the smoke specs; the fixture's file has no `window` field.
- How the renderer gets into the exit path, so that ⌘Q can write every pending Document before the process ends, is ADR-0005's decision.
- The Settings (CONTEXT.md) are not in the Session. They live in a file of their own, `settings.json`, beside `session.json`, owned by the Rust side the same way: the renderer reads it once at launch (`read_settings`) and hands over every change (`update_settings`), and Rust writes it atomically at once, with no debounce, since a setting changes by hand and rarely. The Session is what Plumo brings back; the Settings are what the user chose, and more of them are coming. Deleting `session.json` to start over should not reset them, and a Settings dialog should not have to reach into Tab state to save a theme. The file is checked field by field: a value that fails is replaced by its default and the rest still apply; an unknown `version` gives all defaults. It is not watched while Plumo runs. The theme moved there without a migration: the Session's old `theme` is ignored, and every install starts at the default, `light`, once.
- The theme is a Setting, owned by the renderer: `theme` is the View → Appearance choice, the same value the Settings dialog shows, restored at launch and written on every change. A localStorage mirror of it exists only for the inline script in `index.html` that paints the first frame before the renderer has read the Settings; the theme applier rewrites the mirror whenever the choice changes.
- The sidebar is the renderer's too: `sidebar.collapsed` and `sidebar.width` are restored at launch and written on every change: a toggle, the collapse a lone Document brings, a keyboard step on the edge, or the end of an edge drag (not each pointer move; the Rust debounce is not a reason to send sixty updates a second). A width outside 180–480 is clamped on both the way in and the way out. Unlike the theme there is no pre-paint mirror: the shell is laid out but not painted (`visibility: hidden`) until the restore has settled, so the sidebar and the editor appear once, in their restored state, over the window's own background colour. The restore is one read of a small file and always settles, so nothing is hidden for longer than that.
- The Pinned lists are the renderer's as well: `pinned` maps each Folder's path to its pinned paths in the user's order, and every list rides along in every update, not only the open Folder's, so opening a Folder again gets its pins back. The sidebar's `collapsedSections` (`"pinned"`, `"explorer"`) is the sections folded away under their label; the Explorer's label is the Folder's name. A pin whose file the Folder's listing no longer holds is dropped by the renderer when that Folder is listed; the Rust side still treats all of it as opaque JSON.
- The Recent Folders are the renderer's too: `recentFolders` is the paths of the Folders opened as Folders, most recent first, at most ten, the current one included. Only Open Folder… adds to it; the directory of a Document opened on its own is a boundary root (ADR-0002), not a Folder, and leaves no trace. A path that no longer exists is not checked for when the list is shown; it is dropped when choosing it fails to list the Folder. Choosing one replaces the Folder in the same window, through the same change path as Open Folder…, so the Write failure check and the close of every Tab stay as they are. Opening a Folder in a new window was rejected for v0.1: Plumo has one window, Rust keeps one main frame, and a second window is a change of its own; a setting could choose it later.
- The open Tabs are kept per Folder, like the Pinned lists: `openEditors` and `activePath` are the current Folder's, and `tabsByFolder` maps each other Folder's path to the Tabs and active Tab it had when it was last shown, so a Folder opened again gets its Tabs back. A Tab belongs to the Folder that was open when it was opened, wherever its file lives, so a lone Document opened beside Folder A comes back with A and not with B. This was chosen over keeping Tabs open across a Folder change (the Explorer would show one Folder and the Tabs another) and over closing them for good (the current behaviour; switching back to a Folder would find it empty, which is most of what Recent Folders is for). A Folder's Tabs are dropped when it falls off the Recent Folders; its Pinned list is not, because a pin is a choice the user made and the list is small. The Explorer's expanded folders and scroll are not in the Session today and are not added by this; a Folder opened again starts with its tree folded. Restoring a saved Tab whose file is gone is ADR-0008's rule.
